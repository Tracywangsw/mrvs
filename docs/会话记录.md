## 一、需求拆解

- **主数据**：医药代表（MR）、医生（HCP）、医院、产品。
- **主流程**：计划 → 签到 → 学术沟通 → 签退 → 拜访记录。流程是强状态机，不能跳步，也不能重复。
- **核心价值**：不只要记录“聊了什么”，还要留下“确实到场、时间合理、地点合规”的证据链。
- **硬性交付**：数据库 Schema、四个核心接口、合规算法、桌面端表单、产品月度看板、单元测试、docker-compose。
- **容易漏掉的点**：并发重复签到、时间倒挂、坐标非法、异常原因可解释、时区、医院坐标基准点。

## 二、技术选型

| 层次 | 选型 | 理由 |
|---|---|---|
| 后端 | Go 1.22+ / Hertz v0.9 | 满足指定框架，HTTP 层轻量 |
| 数据访问 | GORM | Schema 清晰、迁移和查询成本低 |
| 数据库 | MySQL 8 | 便于 compose 一键起，JSON 字段存异常原因 |
| 前端 | Vue 3 + Element Plus + ECharts + Vite | 表单和看板开发快，桌面端适配好 |
| 部署 | 多阶段 Docker + 前端 `go:embed` + compose | 单应用镜像 + MySQL，一键启动，无跨域问题 |

分层：`handler`（参数校验）→ `service`（状态机 + 事务 + 合规调用）→ `repository`（GORM）→ MySQL。合规判定放在独立的 `internal/compliance` 包，纯函数、无 IO，方便单元测试。

## 四、状态机与合规算法

状态流转与守卫：

- `planned → checked_in`：仅允许一次签到，必须带合法经纬度。
- `checked_in → checked_out`：仅允许一次签退，服务端时间必须晚于签到时间。
- `checked_out → reported`：提交拜访记录后完成。
- `planned → cancelled`：仅未签到可取消。

合规判定在**签退时**执行，结果快照写入 `visit`，不依赖前端：

```go
type RuleSet struct {
    MinDuration     time.Duration // 默认 5m
    MaxDistanceMeters float64     // 默认 500
}

func Evaluate(v VisitSnapshot, h HospitalPoint, r RuleSet) []Violation
```

判定规则：

| 规则码 | 条件 | 结果 |
|---|---|---|
| `SHORT_DURATION` | 停留时长 < 5 分钟 | 异常 |
| `LOCATION_DEVIATION` | 签到或签退坐标距医院 ≥ 500 米 | 异常 |
| `INVALID_TIME` | 签退时间早于签到时间 | 异常并拒绝 |
| `INVALID_COORDINATE` | 经纬度越界或缺失 | 异常并拒绝 |

距离用 Haversine 公式计算，签到、签退取最大偏差存入 `deviation_meters`。每条异常都会以 `{code, message, measured}` 的格式写入 `abnormal_reasons`，方便前端展示和审计。阈值通过环境变量配置，不硬编码。

并发控制：签到/签退使用事务 + 条件更新（`UPDATE ... WHERE id=? AND status=?`），根据受影响行数判断是否重复提交，避免双击产生两条签到。

## 五、接口设计

统一前缀 `/api/v1`，统一响应 `{code, message, data, request_id}`。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/visits` | 创建拜访计划 |
| GET | `/visits` | 列表，支持 MR、状态、产品、日期、分页 |
| GET | `/visits/{id}` | 详情，含合规结果 |
| POST | `/visits/{id}/check-in` | 签到，body: `latitude, longitude` |
| POST | `/visits/{id}/check-out` | 签退，返回时长、偏差、异常原因 |
| PUT | `/visits/{id}/report` | 提交/更新拜访记录与资料派发 |
| GET | `/dashboard/products?month=2026-11` | 产品维度月度统计 |
| GET | `/meta/{mrs,hospitals,hcps,products}` | 表单下拉数据 |

签到/签退时间默认取服务端时间；为方便演示“短时长异常”，保留一个受环境变量 `ALLOW_TIME_OVERRIDE` 控制的测试入参，生产默认关闭。

## 六、前端页面

1. **拜访列表**：按状态、产品、日期筛选，异常拜访用红色标签标出。
2. **新建计划**：选择 MR、医生、医院、产品、计划时间。
3. **拜访执行页**：五步进度条；签到/签退手动输入经纬度；提交后展示停留时长、偏差距离、命中的异常规则。
4. **拜访记录**：谈话要点、医生反馈、是否派发资料、后续跟进。
5. **月度看板**：月份选择器 + ECharts 堆叠柱状图，按产品展示“正常 / 异常”拜访次数，并汇总总次数与异常率。

统计 SQL 只统计已签退或已记录的拜访，避免把仅计划的记录计入：

```sql
SELECT product_id, COUNT(*) AS total, SUM(is_abnormal) AS abnormal
FROM visits
WHERE status IN ('checked_out','reported')
  AND checkout_at >= ? AND checkout_at < ?
GROUP BY product_id;
```

## 八、关键取舍与风险

- **GPS 手动输入无法防伪**：方案只能保证“记录原始坐标 + 服务端时间 + 判定快照”，无法证明手机真实定位；这是需求明确模拟采集后的固有边界。
- **医院坐标是合规基准**：种子数据必须准确，否则 500 米判定失真。
- **单次拜访对应单产品**：符合“某个具体产品”的描述；若要多产品，需要增加 `visit_product` 关联表。
- **无认证**：按需求不做权限，但会在接口层保留 MR 维度过滤，后续加登录成本低。

```text
mr 1 ── N visit N ── 1 hcp N ── 1 hospital
product 1 ── N visit
visit 1 ── N visit_material
```

`call_report` 已删除，拜访记录不再需要 JOIN。

## 写入时机调整

| 动作 | 写入字段 |
|---|---|
| 创建计划 | `visit_no`、mr/hcp/hospital/product、`planned_at`、`status='planned'` |

| 签退 | `checkout_at`、坐标、`duration_seconds`、距离、`is_abnormal`、`abnormal_reasons`、`status='checked_out'` |

## 约束与接口影响

- `materials_distributed=1` 时，服务层要求 `visit_material` 至少一条，事务内保证一致。
- `PUT /api/v1/visits/{id}/report` 直接更新 `visit` 行，无需再操作独立记录表。
- `GET /api/v1/visits/{id}` 少一次关联查询。
- 看板 SQL 不变，仍按 `visit.product_id + checkout_at` 统计。

如果后续需要保留多次修订记录，再拆回 `call_report` 或增加快照表即可；当前 1:1 场景合并是合理的。

## 查询逻辑

```sql
SELECT product_id,
       COUNT(*) AS total_visits,
       SUM(CASE WHEN is_abnormal = 0 THEN 1 ELSE 0 END) AS normal_visits,
       SUM(CASE WHEN is_abnormal = 1 THEN 1 ELSE 0 END) AS abnormal_visits
FROM visit
WHERE status IN ('checked_out', 'reported')
  AND checkout_at >= ? AND checkout_at < ?
  AND (? IS NULL OR product_id = ?)
  AND (? IS NULL OR mr_id = ?)
GROUP BY product_id;
```

`product_id` 过滤可直接命中现有索引 `idx_product_checkout(product_id, status, checkout_at)`。零值时 `abnormal_rate` 返回 `0`。
